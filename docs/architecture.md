# Architecture notes

This doc collects the deeper rationale behind the node choices and the
16 GB VRAM budget. Skip if you just want to run the build.

## Why Canny (and not Pose or Depth)

The official ComfyUI template ships a **Pose** preprocessor
(`SDPose Video Pose Extractor [Multi-Person]`) built on SDPose. As of
ComfyUI 0.39.0 the SDPose nodes *are* bundled in core
(`comfy_extras/nodes_sdpose.py` — `SDPoseKeypointExtractor`,
`SDPoseDrawKeypoints`), and the weights are downloadable from
[Comfy-Org/SDPose](https://huggingface.co/Comfy-Org/SDPose).

Canny is still the default here because it is built into
`comfy_extras/nodes_canny.py`, uses **kornia** under the hood and needs no
extra weights at all. The model produces reliable edges from any source frame
and gives the controlnet a stable structural cue without losing the
camera/scene context the way Pose would for a single-person subject.

Swapping the preprocessor is a one-node change (see "How to swap
preprocessors" below). The H3 Fun ControlNet-Union was trained on Canny,
Depth, HED, MLSD and Pose, so any of them is a drop-in replacement for node
`800`.

## The controlnet's other modes we are not using yet

`MiniMaxH3FunControlNetApply` also accepts a **`mask`** and a
**`source_video`**. That is the Union checkpoint's video-inpainting path:
regions marked `1` in the mask are regenerated while the rest of the frame
stays fixed, with the source video supplying the surrounding context. It is
the natural fit for Genjutsu's second mode, Object Swap — replace one element
in a shot and keep the camera move, the timing and everything else identical.

ComfyUI 0.39.0 also ships `SAM3_VideoTrack` and `SAM3_TrackToMask` in core
(`comfy_extras/nodes_sam3.py`), which can produce exactly that mask from a
text prompt across a clip. The SAM3 weights are not in core, so this path
needs the community SAM3 pack on top.

## The controlnet checkpoint version

The Union checkpoint we ship is v1 (5 control blocks). A v2 checkpoint
(`minimax_h3_fun_controlnet_union_2.0_pruned_int8_convrot.safetensors`,
4.53 GB) is published alongside it and is the recommended one for new work.
ComfyUI reads the block count and the `control_blocks_places` metadata to tell
the two apart, and v2 additionally supports `inpaint_post_norm`, which
changes how masked holes are filled — relevant to the inpaint path above.
The v1 file is what this repo's demo was rendered with.

## Why downscale Canny to 432×240

Canny at the source's native 864×480 with 124 frames allocates ~3.8 GB on
top of an already-loaded H3 stack (UNet + Qwen3 + controlnet + VAEs). On a
16 GB card that pushes the device limit (15.47 GB PyTorch view with
`--reserve-vram 0.5 --vram-headroom 1`) and PyTorch's caching allocator
fails to find a contiguous 3.8 GB block — even though total fragmentation
budget is technically available.

432×240 cuts the Canny working set to ~600 MB which fits cleanly. The
`MiniMaxH3FunControlPatch._fit_frames` method resizes the control video
to the target output dimensions (`width × height`) on every step, so the
controlnet still produces edges at the resolution H3 generates at.

If you have ≥24 GB VRAM, delete the `ImageScale` node (id `850`) and let
Canny see the source at full resolution.

## Why `MiniMaxH3ReferenceToVideo`'s native audio slots (and not `VRGDG_MiniMaxH3AudioDrive`)

H3's native audio generation produces plausible sound for the prompt
description, but **it does not preserve the source clip's audio**. The
demo output's audio is H3-generated.

The `comfyui-vrgamedevgirl` pack ships a `VRGDG_MiniMaxH3AudioDrive`
node (in `optional_nodes/ltx_minimax_tools/`) that locks the source audio
via three steps:

1. Encode the source audio through the H3 audio VAE into H3's AV latent
   audio slot.
2. Replace the AV latent's audio half with the encoded source. The video
   half is left empty (still to be generated by sampling).
3. Mark the audio half with a **zero denoise mask** so the sampler
   doesn't touch it during the diffusion steps. Only the video half is
   denoised.

After sampling and decode, the audio passes through unchanged into the
muxed output via `CreateVideo` (which combines images + audio into the
final `VIDEO` object that `SaveVideo` writes).

**Audio preservation verified. Output RMS matches source within 0.05 dB
across channels — the VAE roundtrip is essentially lossless for
ambient / music content.**

**Why the upstream node can't load out of the box**: this build targets
a 16 GB card with torch 2.14.1+cu130. The only `torchaudio` cu130
wheels (2.9.0, 2.9.1, 2.10.0, 2.11.0) all require torch 2.9 or 2.10 and
break the torchvision/torch ABI when forced.

The Openjutsu build works around it with a patch file,
`patches/vrgdg-minimax-h3-audio-drive-torchaudio.patch`, which replaces the
single `torchaudio.functional.resample` call with a
`scipy.signal.resample_poly` equivalent (scipy is already a ComfyUI
dependency). `scripts/setup.sh` applies it to the pack after cloning.
Revert it — it's three commented lines — once torchaudio ships a compatible
cu130 wheel.

The patched node lives in the pack, not in this repo, because the pack is
AGPL-3.0 and vendoring its code here would change this repo's licence. The
patch is a diff against the upstream file and applies cleanly to a fresh
clone.

## Why `--lowvram` and **not** `--disable-smart-memory`

`--disable-smart-memory` keeps models resident in VRAM between phases,
which is what triggered the first OOMs. With smart memory on (the
default), ComfyUI offloads models to system RAM when their owning phase
ends and reloads them when the next phase needs them. The `--lowvram`
flag keeps UNet/CLIP in smaller on-device buffers via
`comfy.model_management.load_models_gpu()` chunking.

On this 16 GB card the working combination is:

```bash
--fp8_e4m3fn-unet        # H3 unet to FP8 (saves ~3 GB vs default fp16)
--fp16-vae               # VAEs at FP16 (int8 VAE file is preferred where available)
--lowvram                # chunked model loading
--reserve-vram 0.5       # leave 0.5 GB for system/CUDA context
--vram-headroom 1        # +1 GB reserve on top of reserve-vram
```

`--vram-headroom 1` is the critical knob for fitting H3 + ControlNet in
16 GB; the H3 skill notes the proven default is `--vram-headroom 2` for
the ref2va + reference-image workflow alone, but with the ControlNet
patch loaded you need the extra GB back.

### Two workflow files

| File | Audio |
|---|---|
| `workflows/openjutsu_api.json` | H3's own generated audio. No third-party node needed. |
| `workflows/openjutsu_api_audio.json` | The source clip's audio, preserved, via `VRGDG_MiniMaxH3AudioDrive`. Needs the `comfyui-vrgamedevgirl` pack. |

The web UI picks the second when the VRGDG node is present on the daemon and
falls back to the first otherwise. Set `OPENJUTSU_WORKFLOW=core` or `=audio`
to force one.

### Reference slots and validation

The three `LoadImage` nodes are wired to `ref_images.ref_image_0..2` on the
H3 node. If a slot's file is missing from ComfyUI's `input/` directory,
ComfyUI rejects the *entire* prompt with `Invalid image file` — it does not
skip the node. The web UI therefore always points every slot at a file that
exists (falling back to a bundled example) and removes the `ref_image_N` link
for slots the user did not fill, so H3 never sees an unwanted reference.

## How to extend to multiple reference images

The `MiniMaxH3ReferenceToVideo` node accepts up to **9** reference images
(`ref_image_0` … `ref_image_8`) plus 3 reference videos and 3 reference
audios. To add more, drop additional `LoadImage` nodes in the graph, then
patch the corresponding `ref_images_#N` input in the API-format JSON.

For a "cast swap" demo: use `ref_image_0` for the new character and
`ref_image_1` for the new location/wardrobe. The controlnet still drives
the motion from the source video.

## How to swap preprocessors

Canny is a placeholder. Replace node `800` (Canny) with one of:

- **Depth Anything 3** (`comfy_extras/nodes_depth.py`) — captures scene
  geometry, often more useful than Canny for outdoor clips
- **SDPose** (`https://github.com/comfyanonymous/ComfyUI_experiments` or
  community packs) — skeletal pose, ideal for character motion
- **MLSD** (line segments) — good for architectural scenes
- **HED** (holistically nested edge detection) — soft edges, good for
  organic shapes

All of these feed into `MiniMaxH3FunControlNetApply.control_video`
unchanged. The H3 Fun ControlNet-Union was trained on all five and any
of them work as a drop-in replacement.

## Object Swap: the inpaint path, and what actually makes it swap

Genjutsu has two modes. Motion Transfer rebuilds the whole shot. Object Swap
changes one element and keeps the rest of the original shot. The H3 Fun
ControlNet-Union we already ship has the machinery for the second one: the
`MiniMaxH3FunControlNetApply` node takes a `mask` and a `source_video`
alongside `control_video`, and the ComfyUI docs describe it as *"regions
marked `1` are regenerated under control of the optional `source_video`
input, while the rest of the frame stays fixed."*

### The channel layout

The Union branch is 49 channels wide, not 24:

| Channels | Content |
|---|---|
| 0–23 | control video latent (Canny / Depth / HED / MLSD / Pose), or zeros |
| 24 | visibility map (`1 - mask`, on the latent grid) |
| 25–48 | the source video, VAE-encoded, with the masked pixels zeroed |

The `control_proj_in` weight is `[5376, 196]` — 49 channels x the 1x2x2 patch.
Both the v1 and the v2 Union checkpoints are 49-wide, so the inpaint path
works with either; the difference is the hole convention.

### Use the Union 2.0 checkpoint for Object Swap

| Checkpoint | Metadata | Hole convention |
|---|---|---|
| `..._union_pruned_int8_convrot` (v1) | `minimax_h3_fun_controlnet: adaln_basis` | `pre_norm` — holes land near -2 |
| `..._union_2.0_pruned_int8_convrot` (v2) | `+ inpaint_masked_pixel_mode: post_norm`, 10 control blocks | `post_norm` — holes land at 0, mid-gray in pixel terms |

The upstream reference (`aigc-apps/VideoX-Fun`,
`examples/minimax_h3_fun/predict_v2v_control_inpaint.py`) points at the 2.0
checkpoint and the `post_norm` config, and `alibaba-pai` calls 2.0 the
recommended checkpoint for new work. `Object Swap` therefore uses the 2.0 file.
ComfyUI reads the block count and the `control_blocks_places` metadata and
builds the right injection layers for both.

### Verified: the masked region really does regenerate

Three renders, each isolating one variable:

1. **Whole frame masked**, no reference, prompt *"a robot astronaut in a
   spaceship"*. Result: a completely different image. The masked region is
   regenerated, not copied.
2. **Top ~39% masked** (sky and tree line), no reference, prompt asking for
   night. Result: the masked band changed, the unmasked meadow stayed.
3. **Dancer's body masked**, reference = a different person's face. Result: the
   region regenerated, but it reproduced the original dancer.

Case 3 is the honest limit of the current build. The visibility map pins the
unmasked 85% of the frame, and the model reconstructs the masked region to be
consistent with what surrounds it — so with a static mask and a prompt that
still describes a dancer in a meadow, it renders a dancer. **The swap needs
the prompt to describe the new element, and the reference to be a good match
for the masked region** (a full-body reference for a body mask, not a face
crop). That is the next thing to tune, not a broken pipeline.

### Diagnostics

`MiniMaxH3FunControlNetApply` writes nothing about the control latent, so
"the mask is not doing anything" and "the mask is applied but the model
overrides it" look identical from the outside. Dumping the hint tensor
settles it in one line:

```
DBG control_latent shape=(1, 49, 12, 18, 30) | visibility ch24 min=0.000 max=1.000 mean=0.845
```

49 channels, visibility spanning 0..1 with a mean that matches the masked
area fraction — the mask is reaching the model. If that line shows a
different shape, the mask is not connected.

## Uploading reference images: use the SDK asset API, not bare filenames

ComfyUI resolves a `LoadImage` filename against the **daemon's** input
directory. The web app used to write uploads to a local directory and pass
the bare filename in the workflow — which works only when the app shares a
filesystem with the daemon. Point the app at a different `COMFYUI_INPUT_DIR`
and every render fails with `Invalid image file`, because the daemon is
looking for a file that was never put in front of it.

The fix is to upload through the Comfy SDK asset API:

```python
wf.set_input(node_id, "image", client.assets.from_file(str(path)))
```

The proxy POSTs the bytes to the daemon's own `/upload/image` endpoint and
substitutes the resulting filename at submit time, so the app no longer
assumes a shared filesystem. The submitted graph shows the asset-resolved
name:

```
900: {"image": "ref_3f4579a7_UNIQUE_test_ref.png"}
```

Uploads are staged locally under `web/staging/` first; the staged copy is
what gets uploaded, and the staging directory is transient.

**One gotcha worth knowing**: the proxy keeps a *persistent* asset store and
dedups by content hash. If a file it has already seen is missing from the
daemon's input directory, a re-upload of the same bytes is deduped and never
written back — so the file stays missing and validation fails. If you delete
files out from under the proxy, clear its asset store (or upload different
bytes) as well. This is why an upload that "should" work can appear to be
ignored.
